# Staging on Render (`msg-staging`)

Supabase project or a Redis instance with production (`RENDER_PRODUCTION.md`).

## 2. Environment variables

| Variable | Where it comes from |
|---|---|
| `DATABASE_URL` | Supabase pooler string, port 6543 |
| `REDIS_URL` | Render Key Value internal URL. **Required**: login is throttled, and a throttle with no Redis 500s instead of returning 429 |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | Supabase Storage S3 key |
| `AWS_STORAGE_BUCKET_NAME` | `msg-staging`. If missing, uploads silently go to the container's disk and vanish on redeploy |
| `AWS_S3_ENDPOINT_URL` | `https://<project>.supabase.co/storage/v1/s3` |
| `AWS_S3_REGION_NAME` | The region code from the S3 Connection panel — not the bucket name; a wrong value breaks SigV4 signing |
| `TWILIO_ACCOUNT_SID`, `TWILIO_API_KEY_SID`, `TWILIO_API_KEY_SECRET`, `TWILIO_VERIFY_SERVICE_SID` | Twilio console. Without them, back-office login is refused (no SMS code can be sent) |
| `SENTRY_DSN` | Sentry project (optional, recommended: see §4) |
| `DJANGO_ADMIN_EMAILS` | Comma-separated; unhandled errors are mailed here (needs email set up) |
| `TASK_TRIGGER_TOKEN` | A long random string; only if a scheduled job exists (§3) |
| `DJANGO_SUPERUSER_PHONE` / `DJANGO_SUPERUSER_PASSWORD` | The Django-admin account, created on container start by `ensure_superuser` |

`DJANGO_SECRET_KEY` is generated by Render. `EMAIL_BACKEND` is the console backend on staging.

## 3. Scheduled jobs

None yet. When one is added: a management command, listed in `apps.core.views.TASKS`, triggered
on staging by cron-job.org POSTing to `/internal/tasks/<name>/` with header
`X-Task-Token: $TASK_TRIGGER_TOKEN`. Production gets a Render Cron Job service for the same
command instead (`render.yaml`), never the HTTP endpoint.

## 4. First deploy checklist

1. Deploy, then open `https://msg-staging.onrender.com/healthz/` → `{"status": "ok"}`. The
   health check queries the database, so a bad `DATABASE_URL` shows up here.
2. Confirm errors are visible **before** anyone needs to debug: with `SENTRY_DSN` set, open
   Sentry and check the release appears; otherwise, check Render's Logs tab shows the startup.
3. Create the first two super admins from a machine with `.env.staging` loaded and prod
   settings: `manage.py bootstrap_admin <phone> <nom> <prénoms>`. It assigns Super admin +
   Membre through the audited service and prints a temporary password and PIN once. Done on
   2026-10-20 for both staging admins.
4. Log in at `/bo/` with one of them; the SMS code must arrive.
5. Build the beta app against staging:
   `flutter build apk --release --dart-define=API_BASE_URL=https://msg-staging.onrender.com/api --build-number=N`
   and verify it before sharing (playbook §9: `aapt2 dump badging`, `apksigner verify`,
   not debuggable, the URL present in `libapp.so`, `sha256sum`).

Free tier sleeps after 15 minutes idle; the first request after that takes about a minute.
